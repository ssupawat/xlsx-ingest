# xlsx-ingest

Load an `.xlsx` into an existing SQL table without guessing anything.

The premise: the spreadsheet is already clean, and the person who made it knows
what their data means. So the job is not to infer, repair or coerce — it is to
read each cell literally, check it against the table it is going into, and hand
back a coordinate when something does not fit.

```python
from sqlalchemy import create_engine
from excel_to_sql import excel_to_sql, IngestionError, SourceFileError

engine = create_engine("postgresql://...")
try:
    n = excel_to_sql("orders.xlsx", "orders", engine)          # -> rows inserted
except IngestionError as e:
    print(e)          # every bad cell, with its A1 coordinate
```

`dry_run=True` validates and returns the row count without touching the
database. `target` also accepts a live `Connection` (the caller keeps the
transaction) or a URL string.

## Three rules

**1. No magic.** [python-calamine](https://github.com/dimastbk/python-calamine)
reads cell by cell. No column-level dtype inference, no `NaN`, no `"1"` quietly
becoming `1.0`. The single normalisation left is `5.0 → 5` for an integer
column, because `.xlsx` stores every number as a double — and it stops at 2^53,
where the file has already lost digits.

**2. The database is the schema.** The target table is reflected at runtime with
SQLAlchemy and that is the whole contract: type, nullability, `VARCHAR` length,
defaults. Nothing to declare, nothing to keep in sync.

**3. Errors carry coordinates.** The whole sheet is validated before a single
row is written, and every failure comes back at once — a sheet with four
problems produces four lines, not one exception at the first bad cell. Causes
that repeat down a column collapse into one report.

```
3 cell(s) rejected in 2 distinct problem(s):
  [Sheet!C3] column 'qty': expected INTEGER, got number(2.5) — value has a fractional part
  [Sheet!E4, Sheet!E7] column 'ship_date': expected DATE, got 2 cells — format the cell as Date in Excel
```

## What gets rejected

Beyond plain type mismatches, anything where the file does not say what the
screen shows:

| | |
|---|---|
| `15%`, `฿1,234.50`, `1.2E+03`, `# ?/?`, `;;;` | the cell displays one thing and stores another |
| `#N/A`, `#REF!` | calamine hands these over as `""` — they would land as `NULL` |
| a formula with no cached result | same, and just as invisible |
| the lower half of a merged range | same |
| an integer at or beyond 2^53 | the digits are already gone |
| duplicate or unknown headers, missing `NOT NULL` columns | with a *did you mean* hint |

Blank cells always become `NULL`. `NOT NULL` columns without a default reject
the blank instead.

Only real `.xlsx` is accepted. `.xls`, `.xlsb` and `.csv` hide error cells,
formulas and number formats from these checks, and silently skipping the checks
would be worse than refusing the file.

## If the file comes from SheetJS

`XLSX.read(buf)` / `XLSX.write(wb)` with default options drops every number
format. A viewer still shows `2026-01-05` and `15%`, because SheetJS computed
the display text while reading — but the file it writes holds `46027` and
`0.15` with nothing marking them. Whatever the user approved on screen, that
file can no longer prove it, so it is refused with a `SourceFileError` pointing
at the generator rather than at the user:

```js
XLSX.read(buf, { cellDates: true, cellStyles: true })
XLSX.write(wb, { cellStyles: true })
```

Better still, send the original upload through untouched. `sheetjs/` contains
the round-trip scripts this conclusion came from.

## Tests

```
pip install -r requirements.txt -r requirements-dev.txt
python demo.py            # happy path + a deliberately broken sheet
python stress_test.py     # 27 sheet shapes: ragged rows, offset headers, merges, unicode, ...
python stress_test2.py    # 11 hand-written XML cases for Excel's style inheritance
```

Every fixture is generated by the scripts themselves. They cover the XML shapes
Excel is known to emit, but no file here was actually saved by Excel or Google
Sheets — worth keeping in mind before trusting the style checks in production.

200k rows × 9 columns validate in ~11s using ~130 MB. Inserts are batched inside
a single transaction, so a failure mid-load leaves nothing behind.
