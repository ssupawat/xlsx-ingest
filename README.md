# xlsx-ingest
 
Load an `.xlsx` into an existing SQL table without guessing anything.
 
The premise: the spreadsheet is already clean. The person who made it knows
what their data means. So the job is not to infer, repair or coerce: it is to
read each cell literally, check it against the table it is going into, and hand
back a coordinate when something does not fit.
 
```python
from sqlalchemy import create_engine
from excel_to_sql import excel_to_sql, IngestionError
 
engine = create_engine("postgresql://...")
try:
    n = excel_to_sql("orders.xlsx", "orders", engine)   # -> rows inserted
except IngestionError as e:
    print(e)                                            # every bad cell, with its A1 coordinate
```
 
`dry_run=True` validates and returns the row count without writing anything. `target` also accepts a live `Connection` or a URL string.
 
## Three rules
 
**No magic.** [python-calamine](https://github.com/dimastbk/python-calamine)
reads cell by cell. No column-level dtype inference, no `NaN`, no `"1"` quietly
becoming `1.0`. Normalisation is limited to what is lossless. `5.0` becomes `5`
for an integer column, because `.xlsx` stores every number as a double. A
`date` widens to a midnight `datetime`, and a midnight `datetime` narrows to a
`date`. Integers stop at 2^53. Excel keeps 15 significant digits, so anything
longer is already rounded in the file.
 
**The database is the schema.** The target table is reflected at runtime with
SQLAlchemy and that is the whole contract: type, nullability, `VARCHAR` length,
defaults. Nothing to declare, nothing to keep in sync.
 
**Errors carry coordinates.** Nothing is written before the whole sheet passes
validation. Every failure comes back at once. Causes that repeat down a
column collapse into one report.
 
```
3 cell(s) rejected in 2 distinct problem(s):
  [Sheet!C3] column 'qty': expected INTEGER, got number(2.5); value has a fractional part
  [Sheet!E4, Sheet!E7] column 'ship_date': expected DATE, got 2 cells; format the cell as Date in Excel
```
 
## What gets rejected
 
The loader rejects type mismatches against the target column, and anything
where the file does not say what the screen shows:
 
| | |
|---|---|
| `15%`, `฿1,234.50`, `1.2E+03`, `# ?/?`, `;;;` | the cell displays one thing and stores another |
| `#N/A`, `#REF!` | calamine hands these over as `""`; they would land as `NULL` |
| a formula with no cached result | same, and just as invisible |
| any merged-range cell except its top-left | same |
| an integer at or beyond 2^53 | the digits are already gone |
| duplicate or unknown headers, missing `NOT NULL` columns | unknown headers get a *did you mean* hint |
 
Blank cells always become `NULL`; a `NOT NULL` column without a default rejects
the blank instead. Only real `.xlsx` is accepted: `.xls`, `.xlsb` and `.csv`
hide error cells, formulas and number formats from these checks.
 
## Tests
 
```
pip install -r requirements.txt -r requirements-dev.txt
python demo.py            # happy path + a deliberately broken sheet
python stress_test.py     # 27 sheet shapes: ragged rows, offset headers, merges, unicode, ...
python stress_test2.py    # 11 hand-built cases: style inheritance, sheet rels, container checks
```
 
Every fixture is generated by the scripts themselves. They include XML shapes
openpyxl never writes. But no file here was actually saved by Excel or Google
Sheets.
 
200k rows × 9 columns validate in ~2s using ~335 MB on an Apple M2. Inserts are
batched inside a single transaction, so a failure mid-load leaves nothing
behind. With a live `Connection`, the caller owns the transaction.
